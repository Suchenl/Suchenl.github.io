最近让我反复思考的一个现象是：随着通用多模态模型、Coding Agent 和机器人工具接口越来越强，我们开始看到一些系统不需要专门训练新的机器人策略，就能在仿真机器人基准上取得很亮眼的结果。

这当然令人兴奋。但我越来越想问：**机器人榜单上的成功，究竟距离“人们敢让它在身边长期做事”还有多远？**

我不认为答案是“Coding Agent 不适合机器人”。恰恰相反，我认为它们正在展示一种很有潜力的能力。问题在于，我们可能把三件不同的事情混在一起讨论了：**能通过机器人基准、能控制机器人完成一次任务、能成为可部署且可持续使用的机器人 Agent。**

## Coding Agent 与 Robot Agent 的本质区别

为什么会产生这种差距？我觉得应该先看看两类 Agent 工作时面对的环境与约束。两者都能规划、调用工具、处理反馈，但**控制数字环境与控制物理世界，犯错的后果和需要满足的条件并不一样**。


| 维度 | 典型 Coding Agent | 真正可部署的 Robot Agent |
| --- | --- | --- |
| **工作环境** | 主要操作文件、程序与数字状态；许多步骤可以复制、测试、重跑 | 操作真实物理世界；环境随动作、时间和外界干扰持续变化 |
| **失败代价** | 很多错误可通过回滚版本、修复代码或重试恢复；外部服务操作也有不可逆风险 | 可能造成碰撞、掉落、损坏甚至人员伤害；部分后果不能回滚 |
| **反馈与验证** | 编译、单测、程序日志往往提供相对明确的检查信号 | 视觉、触觉、本体状态存在噪声、遮挡和延迟；“运动已完成”不等于“任务已完成” |
| **时间约束** | 通常允许秒级甚至分钟级思考；具体仍取决于在线服务的时限 | 接触、避障、稳定控制等环节可能要求毫秒到百毫秒级响应，任务规划则可以更慢 |
| **行动与环境关系** | 程序的逻辑大多可以先构造，再执行和测试 | 每个动作会改变下一次决策的初始条件，连续动作期间也需要监控 |
| **程序复用** | 在受控软件环境下，相同代码通常更容易重现行为 | 同一动作序列会受到定位误差、摩擦、物体差异及人类介入影响 |
| **安全边界** | 沙盒、权限、测试与回滚可以限制部分风险 | 还需要物理运动约束、独立监测、可抢占执行、故障安全和场景级风险评估 |
| **最终验收** | 任务完成、测试通过、产出正确、成本可接受 | 在预期使用环境中长期、安全、可恢复且经济地完成真实任务 |

*这张表比较的是两类系统所面对的典型工程要求，而不是断言 Coding Agent 天生不可靠、Robot Agent 必须具有某种固定架构。Coding Agent 也会操作不可逆的线上系统；机器人也可以在高度结构化的工位上可靠执行预先编写的代码。*

这张表真正想强调的，不是谁天然更智能，而是**评判标准已经变了**。一个能编写、执行并修复机器人操作程序的 Agent，完全可能在受控任务中表现出色；但要把同样的能力带到长期运行、有人干预且失败不可轻易回滚的环境，还需要另外一套证据。

## 榜单成功率究竟证明了什么？

一个很好的例子是 [PyRUA-Lean](https://arxiv.org/abs/2610.01939)，2026 年 10 月公开的论文 *Fewer Tokens, Better Action*。

它让通用模型不再每执行一个小动作就单独调用机器人工具，而是生成可运行的 Python cell，组合现有运动、夹爪、视觉与部分 VLA 原语；程序内部还能检查结果、有限重试，并选择将哪些信息返回模型。它的确具有实际的程序内反馈，不应该被误解为“生成一长串动作后盲目开环执行”。

在作者的 **700 个仿真任务实例**上，相同 GPT-6 Astra 规划模型和底层原语的条件下，PyRUA-Lean 的成功率为 **71.7%**，对应的逐项工具调用基线为 **63.1%**。在**双方都成功**的实例中，平均 LLM 调用次数从 17.0 降至 8.7，平均输入 Token 从 788K 降至 276K。[来源：论文与官方项目主页](https://dagroup-pku.github.io/PyRUA-Lean/)。

我认为这是有意义的进展：**相同的模型能力，在不同的执行与反馈组织方式下，可以产生截然不同的效率和成功率。** 这也提醒我们，频繁调用大模型未必等于更强的闭环智能。

**这项工作也并非只有仿真。** 作者在 2026 年 10 月 21 日公开了 AF8 双臂机器人的两次**完整、未经剪辑的真机演示**：任务都是把桌上的五个积木全部放进碗里，两次均完成 5/5；分别运行了 41、42 个 Python Cell，耗时 21 分 34 秒和 22 分 39 秒。运行采用 GPT-6 Astra 编写 Cell，并调用视觉、运动规划、夹爪及力/力矩保护原语，不使用 VLA。[真机视频与实验说明](https://dagroup-pku.github.io/PyRUA-Lean/#real-robot) · [官方仓库记录](https://github.com/DAGroup-PKU/PyRUA-Lean)。这确实证明该框架能够驱动真实硬件执行非平凡任务，不能再称之为“完全没有上真机”。

但这个实验和演示仍没有自然推出两个更强的结论：

1. **没有证明 Python 是关键原因。** 它同时改变了决策粒度、原语组合、局部恢复和反馈组织；相较所选基线的优势不能全部归因于“代码比 Tool Calling 好”。
2. **真机演示也不等于已验证长期部署。** 两条成功的真机轨迹证明了可运行性，却没有提供跨任务、多环境、持续运行、安全事件、失败恢复率或维护成本的系统性统计。71.7% 对 63.1% 的比较本身仍来自仿真，不能作为真机成功率。

更广泛地说，[What Are We Actually Benchmarking in Robot Manipulation?](https://arxiv.org/abs/2606.04233)（2026）审计了 LIBERO、CALVIN、SimplerEnv、RoboCasa 和 RoboTwin 2.0 等基准，指出 *shortcut solvability*（捷径可解性）、统计显著性不足、持续调参造成的过拟合和数据来源依赖，可能削弱单个分数对通用操作能力的解释力。这不是说这些基准没有价值；事实上，RoboTwin 2.0 也通过多维域随机化尝试增强鲁棒性。真正的问题是：**一个指标可以很好地度量特定实验协议下的成功，却未必足以度量整个产品生命周期内的可用性。** [RoboTwin 2.0 原论文](https://proceedings.mlr.press/v306/chen26j.html)。

## 物理世界不会因为代码写对了就按预期运行

软件中的测试失败与物理任务失败，有一个容易被忽略的区别：**现实动作会不断改变问题本身。**

假设一个 Agent 要将杯子放入柜子。模型可以提前写好“定位杯子、接近、闭合夹爪、抬起、移动、释放”的程序，甚至添加抓取失败时的条件重试。

但如果抓取途中杯子发生滑动，新的状态可能已经超出了最初的程序假设。如果有人突然进入机械臂运动范围，之前合法的目标轨迹也可能不再安全。如果夹爪到达了预期宽度，也不能由此断言物体一定已被抓住。

程序完全可以读取传感器、循环检测和重新规划。**因此，“写代码”不是根本问题。根本问题是：这些关键判断是否在正确的时间尺度上、根据足够新鲜且可信的物理证据发生。**

我更倾向于把机器人系统拆成三个时间尺度：

| 决策时间尺度 | 主要责任 | 比较合理的承担者 |
| --- | --- | --- |
| 高频连续控制 | 轨迹跟踪、接触响应、关节与力约束 | 可信的实时控制器与专用策略 |
| 中频执行监督 | 是否到达、是否偏离、是否需要中断或重试 | 机器人状态机、监测器、短时闭环技能 |
| 低频语义决策 | 目标解释、任务规划、策略切换、异常原因分析 | 通用多模态 Agent，必要时使用工具 |

这不是固定频率标准，而是一种职责分离：不同硬件、任务和风险等级会改变合理的时间预算。

值得注意的是，成熟机器人软件早已采用类似的分层。例如 [MoveIt Servo](https://moveit.picknik.ai/main/doc/examples/realtime_servo/realtime_servo_tutorial.html) 提供伺服控制以及可选的碰撞、奇异位形和运动限制处理；[Nav2](https://docs.nav2.org/) 则把导航任务、路径控制、重规划和恢复行为拆成不同组件。它们不是通用 Robot Agent 的最终答案，但说明**代码、规划和闭环控制本来就可以共存，无须由同一个 LLM 调用统一承担全部责任**。

## 代码沙盒保证的是软件权限，不是物理安全

我觉得这是 Coding Agent 方法在机器人场景里最容易出现的概念迁移错误。

一个 Python 沙盒限制 import、文件访问和对仿真器内部对象的访问，确实能降低代码执行风险。PyRUA-Lean 有这些限制，也记录了原语调用与执行结果；这都是值得肯定的工程设计。[官方执行说明](https://dagroup-pku.github.io/PyRUA-Lean/docs/getting-started/how-it-works/)。

但即使每一条原语都是“合法 API”，它们的连续执行仍可能产生危险动作。软件层面的**执行权限合法**，不等于物理层面的**轨迹安全**；单个动作不超限，也不等于整段任务在动态环境中没有风险。

具体的风险控制不能只依靠 Agent 事先写出若干 `if` 判断。它需要不依赖大模型是否及时响应的监测、限速、停止机制以及适用于实际场景的风险评估。比如 [Nav2 Collision Monitor](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/core_servers/collision_monitor/) 会绕过常规规划路径执行额外的碰撞监测，但它自身也明确不等于具有硬实时安全认证的保护系统。

工业机器人方面，[ISO 10218-2:2025](https://www.iso.org/standard/73934.html) 把安全要求放在**完整的机器人应用与工作单元**层面，而不是仅评价单个运动算法。需要说明的是，这项标准有明确的工业适用范围，并不能直接作为家用服务机器人的合规证明。

所以我关心的不是“有没有 Python 沙盒”，而是：**当模型、程序、传感器、通信乃至执行器出现错误时，谁拥有最后的物理停止权？**

如果答案是“再调用一次模型，让它想想怎么办”，那在不少真实场景里已经太晚了。

## 我们到底在测模型的物理智能，还是工具的能力？

还有一个研究评价问题。

设想两个 Agent 使用同一个机器人：

- A 只能调用小幅末端位姿变化，并自己判断何时观察、如何修正。
- B 可以调用一个已经高度优化的 `pick_and_place(object, target)`，内部包含定位、抓取规划、避障、重试和放置验证。

如果 B 成功率更高，这是非常好的**系统能力**。但它没有自动证明 B 背后的语言模型具有更强的**物理智能**。

同样，Coding Agent 可以把感知算法、几何运算、已训练策略和执行原语有效组合起来。这是值得研究的组合能力，不应该因为“用了工具”就被否定。但评价时必须说清楚：**能力究竟由模型决策、现成技能、环境接口，还是控制器贡献？**

我认为至少应该区分三种研究主张：

| 研究主张 | 实际应该证明什么 |
| --- | --- |
| **Harness 更好** | 固定模型权重和可用原语，改变上下文、工具组织或反馈后，系统表现更好 |
| **模型更聪明** | 固定 Harness 和工具能力，模型或训练方式改变后仍具有稳健增益 |
| **机器人更可部署** | 在预期物理环境、风险与使用时长下，整套系统满足安全、可靠性和维护要求 |

这三种主张都可能很有价值，但不能用同一个榜单成功率互相替代。

## 我赞成 Coding Agent 做机器人研发，但不认为运行时必须不断生成代码

这也是我想给 Coding 路线一个更公平的定位。

**机器人开发阶段**，Coding Agent 的能力非常有吸引力：生成新的技能、编写视觉工具、调试规划器、自动测试、分析失败轨迹，甚至产生可复用的机器人程序。这些程序可以先在仿真中验证，再做安全审查，最后作为受控技能投入实际运行。

**机器人执行阶段**，即使仍允许模型动态生成代码，也应进一步说明：代码能调用什么、能连续执行多久、如何观察、在哪些事件下必须让出控制权、是否允许跨机器人执行，以及哪个独立组件可以立即取消动作。

我不认为“运行时动态写代码”必然错误。有些任务就是需要临时算几何、组合新工具或生成一次性规划。问题是，它不应因为在软件 Agent 中好用，就被默认为所有物理交互的最佳基本单位。

同理，我也不认为传统 Tool Calling 天然正确。每个关节移动几毫米就完整调用一次多模态大模型，既低效，也可能拖慢响应。**代码与 Tool Calling 只是表达和组织行为的两种形式，真正重要的是它们如何分配感知、决策、执行、监控与安全责任。**

## 什么证据才会让我相信一个 Robot Agent 真能部署？

比起只看某个 benchmark 的成功率，我更想看到一份清晰的**真实部署证据清单**。这里列的是我认为有研究意义的评价维度，不是已有统一的行业标准。

| 维度 | 应该报告的证据 | 为什么比单一成功率更进一步 |
| --- | --- | --- |
| 任务有效性 | 不同任务难度、环境与机器人上的真实完成率及置信区间 | 确认系统不只熟悉某一小组场景 |
| 长期可靠性 | 连续运行时长、任务完成数量、故障/人工接管频率 | 单次成功不代表长期稳定 |
| 扰动恢复 | 物体滑落、目标改变、遮挡、定位漂移后的恢复率与恢复时间 | 测量对意外变化的适应能力 |
| 安全 | 碰撞、危险接近、越界、异常停止、独立保护的触发与覆盖情况 | 安全事故不能只被平均成功率掩盖 |
| 时延与实时性 | 端到端任务耗时、决策延迟分位数、停止响应时间 | 少 Token 不必然意味着真实任务更快 |
| 经济性 | 每成功任务的推理、传感、执行、人工介入和维护总成本 | API 调用费用只是一部分 |
| 可维护性 | 技能迁移、现场重新标定、故障定位、版本升级代价 | 实际使用不可能每次依赖研究者在场 |

特别需要防止一种乐观的统计错觉：如果每次独立执行一个步骤的成功概率都是 99%，那么一项必须连续成功 100 个步骤、不能恢复的任务，其总成功概率只有约 36.6%。这里的独立同分布和不可恢复都是刻意简化的假设，并非现实系统的可靠性估计。

它只是说明：**在长程任务中，看起来很高的单步成功率，也不保证长时间稳定完成。** 真正的机器人当然可以恢复，因此恢复策略、失败代价和人工接管率也必须一起测。

另外，高可靠性不是用少量无事故 Episode 就能证明的。如果目标风险极低，还需要足够的暴露时长、故障注入、置信度分析以及适用的工程安全验证，而非仅靠一个无碰撞率的点估计。

## 一个我更想看到的实验：把 Coding 的收益真正拆开

如果要严肃研究“代码式机器人 Agent 是否更好”，我觉得至少应该在相同模型、机器人能力和任务分布下拆开四个因素：

1. **动作表达形式**：类型化 Tool Calling，还是 Python 编排原语？
2. **决策粒度**：每条动作重新调用模型，还是允许受限的多步程序与局部恢复？
3. **观测与反馈**：自动多视图回传、按需观察，还是仅回传关键物理证据？
4. **执行安全与预算**：模型调用次数、物理动作数、仿真步数、墙钟时间、安全规则是否一致？

只有这样，才能回答“模型写代码真的更好吗”，还是“模型少被打断、上下文更干净、内部控制器做了更多工作”才是关键。

我还想在仿真分数之外加入专门设计的真实扰动与长时间运行测试：在没有改动模型或手工修复程序的情况下，机器人面对环境变化，什么时候自动恢复，什么时候请求重新规划，什么时候安全终止。

这类实验的研究价值，或许不在于再刷高几个百分点，而在于**找出 Agent 该拥有多少自主权、在什么证据出现时必须重新思考，以及哪些能力应该内化进模型、哪些应该交给可信控制系统**。

## 我更看好的方向：让机器人学会什么时候该思考

讨论到这里，我的立场逐渐变得清楚。

我并不反对通用模型写机器人代码，也不否认 PyRUA-Lean 这样的工作已经展示了有意义的系统收益。甚至在适当的权限、控制和验证下，代码生成完全可以是 Robot Agent 的一个重要能力。

但我不希望“把物理任务翻译成一段可执行代码”成为机器人智能的最终定义。真正使我感兴趣的，是机器人能否在**感知、推理、行动与反馈**之间建立可靠、经济、能够长期持续的闭环。

某些动作需要毫秒级响应，却不值得调用一次大模型；某些异常虽然只发生一次，却值得完整重新观察和推理；某些重复经验，最好最终成为参数化的快速反应，而不是下一次仍然重新编写代码。

我越来越觉得，通用机器人 Agent 的关键研究问题可能不是“使用 Coding 还是 Tool Calling”，而是：

> **面对一个持续变化的物理世界，Agent 应该在何时思考、观察和重新规划，又应该在何时信任已经验证的控制能力继续行动？**

Coding Agent 越来越会“让机器人把任务做成”，这是重要进步。但**能完成任务、能在榜单上获胜，与能够安全、可靠、经济地被人长期使用，并不是同一件事**。

当这些边界逐渐被研究清楚，我们才更有理由相信，眼前的不只是一个会调用机器人 API 的 Coding Agent，而是一个真正可以进入现实世界的 Robot Agent。
